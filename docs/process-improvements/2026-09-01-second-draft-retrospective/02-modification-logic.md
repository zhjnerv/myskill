# 修改逻辑

## 一、把“落点台账”升级为“关系台账”

新增 `cn-patent-feature-ledger/v2`，保留 v1 仅用于旧案件回放。v2 中每个技术特征除了名称、证据和文书落点，还必须记录：

```text
动作阶段
→ 输入对象
→ 处理主体
→ 处理动作
→ 输出对象
→ 下游特征
→ 关联异常路径
```

顶层再记录三类跨特征关系：

- `claim_data_flows`：逐项独立权利要求登记入口、顺序链、汇合点、正常出口、异常出口和存储点；
- `method_system_pairs`：方法独权与系统独权的必要特征集合，确保系统模块不是名称平移而是覆盖同一数据链；
- `exception_paths`：按“触发—动作—结果值—置信度—终态—原因码—存储字段”闭合。

机器校验只判断字段是否齐全、引用是否存在、阶段顺序是否自洽、方法—系统登记是否覆盖；是否属于必要技术特征、是否清楚、是否得到支持仍进入语义审查。

## 二、在权利要求完成后增加“数据流复算门”

`build_feature_ledger.py` 对 v2 台账增加以下硬失败：

- 独立权利要求没有入口、正常出口或完整顺序链；
- 顺序链引用未登记特征或出现重复；
- 预配置动作被登记为运行时动作，或阶段顺序倒退；
- 方法—系统对照中的必要特征未同时落入对应独权；
- 系统侧落点未标明处理模块/主体；
- 异常路径缺少终态、原因码或存储字段；
- 产生结果值的异常路径没有置信度；
- 台账声明的下游关系无法在 claim data flow 中找到。

报告新增 `evidence_scope`，明确“文本定位和结构关系通过”不等于法律支持、清楚性或创造性成立。

## 三、把绘图合同从“元素清单”升级为“阅读合同”

新增 `cn-patent-drawing-brief/v3`。每幅图必须冻结：

- `primary_question`：该图唯一回答的问题；
- `reading_direction` 与 `layers`：主阅读方向和层级；
- `complexity_budget`：技术元素、关系、判断节点上限；
- `normal_exit_ids` / `exception_exit_ids`：正常和异常出口；
- 每个元素所属层级；
- 每条关系的独立 `route_channel`；
- `spec_assertions`：说明书中声称该图表达的元素 ID 和关系 ID。

校验器执行双向核对：正文声明的对象必须存在于图合同；图中的技术元素和关系必须被说明书声明覆盖。复杂度超预算时停止制图，要求拆图，禁止用回钩、长说明文字或共享拥挤汇合区补救。

## 四、把视觉复核从“自报 PASS”升级为“受约束观察记录”

新增 `cn-patent-drawing-visual-review/v2`：

- 顶层绑定 drawing brief SHA-256；
- 每图同时绑定最终 PNG 和 export report 的路径、SHA-256；
- 记录 100% 检查和缩小检查的比例；
- 每个检查项不仅为 `true`，还必须有非空观察记录；
- 复核时间、复核者、显示方式进入证据。

最终验证器要求：合同、母版、官方导出报告、最终 PNG、视觉记录五者一致；任一变化都使旧复核失效。

## 五、把 DOCX 变成可复算的末端产物

DOCX assembly report 升级为 v2：

- 逐一记录权利要求书、说明书、摘要、附图索引、每幅嵌入图片和模板的 SHA-256；
- 记录输出 DOCX 哈希；
- 增加 `evidence_scope`，只声明结构、样式、公式对象和图片嵌入检查范围；
- 新增独立验证脚本，从磁盘复算所有输入和输出哈希，源文件或图片变化即判旧 DOCX 证据失效。

## 六、流程顺序调整

```text
阶段2门（检索/IPC/范本）
→ feature ledger v2
→ 权利要求草案
→ claim data flow 复算
→ 说明书草案
→ 台账/说明书/权利要求复算
→ drawing brief v3
→ 图文关系双向门
→ Draw.io 制图与官方导出
→ visual review v2
→ drawing verification
→ 综合审查 prepare/finalize/verify
→ DOCX 组装
→ DOCX 新鲜度复验
```

任何上游工件变化后，从第一个受影响门开始重跑，不允许沿用旧 `PASS`。
